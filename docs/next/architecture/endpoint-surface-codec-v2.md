# Endpoint surface codec v2

Status: recorded generation-scoped extension under the accepted 2026-10-04
no-floor decision ([Nested panes](nested-panes.md)). Awaiting reviewer
reconfirmation; not a new authority.

## Decision

Nested panes add a pane whose content is an extension view. The client must know
each view pane's content identity and the terminals it covers, and the existing
`shell.surface.v1` frame cannot carry them without changing its byte shape. The
surface lane therefore moves to one new codec name, `shell.surface.v2`.

Authority: the human accepted **option B, "no compatibility floor while Vqro is
in development,"** on 2026-10-04 ([Nested panes](nested-panes.md), Decisions).
That entry says the design may change the client protocol and the frozen
generation-1 formats and fixtures freely, older clients are not supported, and
it requires this `AGENTS.md` reconciliation and the fixture disposition below.

## Synced baseline and version axes

This port starts from private protocol **24**, endpoint generation **2**, and
session **v8**. The terminal-admission change already retired generation 1 and
private 22/23 without changing named codec payloads. Keep generation **2**: the
new surface is negotiated independently by its codec name. Private protocol
becomes **25**, because the bincode-reachable `ServerMessage` enum now has the
new surface variant; private 24 is refused before decoding its hello body.
Session **v9** adds view nodes, independently of either transport version.
Generation-1 peers still receive the earlier generation refusal before codec
selection. The v1-only codec refusals below apply to generation-2 peers.

## Why the payload cannot be added in place

`ServerMessage` is bincode behind a `u32` length prefix, with a frozen variant
order for endpoint generation 1. Its only extensible carrier is
`EndpointControl { kind: String, data: String }`, a UTF-8 JSON envelope on the
control writer lane; the surface is a large bincode frame (`CellData` per cell)
on the render lane. Two facts force a new codec name rather than a field on the
v1 frame:

1. bincode cannot add an optional field to a struct on a live lane. A field the
   serializer skips desynchronizes the reader (`UnexpectedEnd`).
2. The endpoint hello checks generation and codec names only. It does not carry
   the private `PROTOCOL_VERSION`, so peers in the same endpoint generation could
   claim the pane surface lane and then disagree on the struct.

Routing per-frame surfaces through the JSON `EndpointControl` envelope would
also put them on the control lane's ordering and drop semantics and rework the
retained-surface, patch and graphics-asset paths. It is not the smaller change.

## What changes

- One `ServerMessage` variant is appended after `EndpointControl`:
  `PaneSurfaceV2(PaneSurfaceFrameV2)` (bincode tag 21). Tags `0..=20` are
  unchanged.
- `PaneSurfaceFrameV2 { frame: PaneSurfaceFrame, views: Vec<PaneSurfaceViewEntryV2> }`
  carries the unchanged v1 frame value plus
  `PaneSurfaceViewEntryV2 { pane_id, extension, view, scope }`.
- `PaneSurfacePane` returns to its terminal-only shape and
  `PaneSurfaceFrame` / `PaneSurfacePatch` bytes are unchanged. Patches stay the
  plain `PaneSurfacePatch` for both codecs: view descriptors change only with a
  topology change, which forces a new full surface.
- Serving is `shell.surface.v2` only: the hello advertises `shell.surface.v2`
  only, the server requires `shell.surface.v2` in the hello, the welcome names
  `shell.surface.v2`, and `shell.surface.v1` is retired **from serving**, not
  from decode.
- Refusals are client-local. A generation-2 peer that advertises only
  `shell.surface.v1` is refused by this server at the greeting with the hello
  rejection `unsupported_surface_codec` ("update this client"). A new client
  meeting a predecessor server that speaks only v1 is refused at the greeting by
  the predecessor with `no_common_core`: the client no longer lists v1, so there
  is no common core codec, and the predecessor never selects a v1 welcome. The
  client's own welcome check (a welcome naming only `shell.surface.v1` fails with
  "update this machine") is a defensive guard that should not fire on the normal
  path. No v1 frame or patch is sent, no shared geometry changes, and no
  supported client is disconnected.
- The pane API names its content kind: `api::schema::PaneInfo` gains
  `content: PaneContent { terminal, view, unknown }`, and `terminal_id` becomes
  optional and is absent for a view (never the empty string). An omitted
  `content` means `terminal`, so a terminal pane's info is byte-identical, and
  `unknown` is the safe fallback for a kind a client does not know. The generated
  `docs/next/api/vqro-api.schema.json` is regenerated in the same commit. The
  inherited `docs/next/api/herdr-api.schema.json` (protocol 22) is deliberately
  **not** regenerated by Vqro API changes: it is the received Herdr generation-1
  snapshot, and Vqro's live shape lives only in the generated schema.
- Fences: `api_pane_focus_on_a_view_succeeds_without_an_error_after_mutation`
  and `terminal_pane_info_omits_the_content_kind_and_stays_unchanged`.

## Serving policy

`shell.surface.v1` is retired from serving, not from decode: serving is
`shell.surface.v2` only. The client advertises only `shell.surface.v2`; a
predecessor server therefore refuses the greeting with `no_common_core` before
it can emit a v1 welcome. A generation-2 peer that advertises only
`shell.surface.v1` is refused by this server with the hello rejection
`unsupported_surface_codec` ("update this client"); the client's welcome check
("update this machine") is a defensive guard for an invalid welcome, not the
normal predecessor path. No v1 frame or patch is sent to any peer, no shared geometry changes,
and no supported client is disconnected. This applies the 2026-10-04 option-B
entry: older clients are not supported and mismatched client and server refuse
cleanly, and no mixed-version client can exist today (remote use is disabled and
every real client ships from the same binary), so a v1 fallback would serve no
client at the cost of a second projection path. Read this with the removal
condition below when the surface lane is re-cut.

## Fixture and expectation disposition

Preserved, not re-blessed: the `_v1` endpoint fixtures, the
`PaneSurface` / `PaneSurfacePatch` bincode decodes and tags 13/19/20, and every
historical value digest. New serving-policy behavior is covered by new tests
with new names (`v1_only_shell_hello_is_refused_client_locally_without_a_surface`,
`pane_surface_v2_frame_round_trips_view_descriptors`), never by editing a frozen
expectation in place.

## Removal condition

Remove `ServerMessage::PaneSurfaceV2` and the `shell.surface.v2` name when the
surface lane is re-cut (a later endpoint generation). Until then this is the
only recorded append to the historically frozen `ServerMessage` enum.
